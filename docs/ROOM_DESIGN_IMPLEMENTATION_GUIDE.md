# ROOM Design — техническая инструкция и спецификация текущей сборки

Версия документа: 20 сентября 2026 года  
Проект: ROOM Design / tenant `norrmobler`  
Рабочий сайт: `https://norr-club.testaimoblernorr.chatgpt.site`

## 1. Назначение документа

Этот документ описывает фактическую архитектуру и пользовательские сценарии текущей сборки ROOM Design. Его можно использовать:

- как инструкцию для разработчика в соседней ветке;
- как источник истины при добавлении нового функционала;
- для переноса сайта на другой домен или создания нового tenant;
- для проверки, что дополнение не ломает существующие сценарии;
- как карту API, хранилищ и ключевых файлов проекта.

Документ описывает не только интерфейс, но и передачу данных между браузером, backend, OpenAI, каталогом NORR, D1 и R2.

> Важно: секретные ключи, пароли и токены нельзя хранить в исходном коде, документации или клиентском JavaScript. Здесь перечислены только названия переменных окружения.

## 4. Общая архитектура

```text
Браузер пользователя
        |
        v
React-интерфейс: app/page.tsx
        |
        +--> /api/auth/* --------> D1: users, sessions, memberships
        |
        +--> /api/projects/* ----> D1: projects + R2: project assets
        |
        +--> /api/catalog -------> YML NORR + 30-минутный memory cache
        |
        +--> /api/generate ------> OpenAI Images API
        |                              |
        |                              +--> результат WebP в R2
        |                              +--> учёт токенов/стоимости в D1
        |
        +--> /api/proposal ------> PDF в памяти -> application/pdf
        |
        +--> /api/objects -------> OpenAI Responses API, background job
        +--> /api/segment -------> Roboflow SAM

```

Все критические внешние запросы идут через backend. Браузер не должен знать API-ключи.

## 5. Мультитенантность

### 5.1. Основная идея

Одна кодовая база обслуживает несколько независимых клиентов — tenants. У каждого tenant могут быть:

- собственный домен;
- собственные пользователи;
- собственные проекты;
- собственные генерации;
- собственный каталог и брендинг в будущем;
- отдельная статистика и администраторы.

Текущий tenant:

- ID: `tenant_norrmobler`;
- slug: `norrmobler`;
- привязан к текущему production hostname.

Tenant определяется на backend по hostname запроса. Если сопоставление не найдено, используется tenant `norrmobler` как безопасное значение текущей сборки.

### 5.2. Изоляция данных

Любой запрос к проекту, генерации или административным данным проверяет одновременно:

- пользователя;
- tenant;
- право доступа к записи.

Префикс объектов в R2:

```text
tenants/{tenantSlug}/users/{userId}/...
```

Нельзя запрашивать объект только по ID без проверки tenant и владельца.

## 6. Авторизация и личный кабинет

### 6.1. Регистрация

Поля формы:

- имя — обязательно;
- фамилия — опционально;
- email — обязательно, одновременно является логином;
- пароль — минимум 8 символов;
- телефон — опционально;
- компания / должность — опционально.

Пароль хешируется на backend через PBKDF2 SHA-256, 100 000 итераций. В базе не хранится открытый пароль.

Сессия:

- cookie `room_session`;
- HttpOnly;
- Secure;
- SameSite=Lax;
- срок жизни 14 дней.

### 6.2. Личный кабинет

Показывает:

- персональное приветствие;
- список сохранённых проектов;
- сохранённые изображения;
- статистику использованных токенов;
- возможность создать новый проект;
- возможность продолжить сохранённый проект.

Проект появляется в кабинете только после явного сохранения пользователем.

## 7. Проекты и история генераций

### 7.1. Жизненный цикл проекта

1. Пользователь создаёт проект.
2. Загружает интерьер или создаёт визуализацию из планограммы.
3. Выполняет операции добавления, замены, удаления или апскейла.
4. Каждая успешная операция добавляет версию в историю генераций.
5. Пользователь нажимает «Сохранить».
6. Backend сохраняет состояние проекта и изображения.
7. Проект появляется в личном кабинете.

### 7.2. История

- Текущий лимит истории при сохранении проекта — 8 версий.
- При загрузке нового интерьера существующая история не должна очищаться.
- Клик по версии делает её активной.
- Новая операция применяется к активной версии.
- Меню апскейла доступно сразу после загрузки интерьера и после каждой генерации.

### 7.3. Сохранение

Интерфейс отправляет в `/api/projects/[id]`:

- исходное изображение;
- активное изображение;
- историю версий;
- активную версию;
- имя файла интерьера;
- соотношение сторон;
- prompt;
- preserved-настройки;
- creativity;
- состояние планограммы и ссылки на материалы.

### 7.4. Известное ограничение

Текущий серверный тип сохранённого состояния фактически фиксирует изображения, историю и параметры генерации, но ещё не сохраняет полностью:

- `planItems`;
- `planRoom`;
- `planFloorReference`;
- `planWallReference`.

Клиент эти поля отправляет, однако backend их сейчас отбрасывает при сериализации. При разработке соседней ветки это нужно исправить до расширения планограммы, иначе план будет потерян после повторного открытия проекта.

## 8. Раздел «Мебель»

### 8.1. Общий интерфейс

Основное изображение имеет три переключаемых режима в одной панели:

- «Добавить»;
- «Заменить»;
- «Удалить».

Панель режимов и нижняя инструкция появляются при наведении курсора на изображение и скрываются после ухода курсора, чтобы не перекрывать интерьер.

Справа располагается панель загрузки интерьера, референса и выбора каталога. Она не исчезает при переключении режима, но недоступные действия могут быть неактивны.

### 8.2. Загрузка интерьера

1. Пользователь нажимает «Загрузить интерьер».
2. Браузер читает выбранный локальный файл.
3. Изображение показывается как основное и как миниатюра в панели.
4. Создаётся первая версия истории: «Исходное изображение».
5. Вычисляется соотношение сторон.
6. Для дальнейшей генерации выбирается поддерживаемый размер:
   - квадрат: `1024x1024`;
   - горизонтальный: `1536x1024`;
   - вертикальный: `1024x1536`.

Оригинальное соотношение сторон нельзя произвольно менять. UI использует `object-fit: contain`, а backend нормализует только допустимый размер результата.

### 8.3. Установка точки

- Левый клик по изображению ставит точку операции.
- Повторный клик по самой точке удаляет её.
- Точка хранится как нормализованные координаты `x` и `y` от 0 до 1.
- Поэтому координаты сохраняют смысл при изменении визуального размера изображения.
- На backend вокруг точки создаётся локальная маска воздействия.

Точка означает:

- в режиме «Добавить» — центр нового предмета;
- в режиме «Заменить» — центр существующего предмета;
- в режиме «Удалить» — предмет, который нужно убрать.

## 9. Механика загрузки референсов

### 9.1. Добавление по референсу

1. Пользователь выбирает режим «Добавить».
2. Ставит точку в месте установки.
3. Нажимает «Загрузить референс».
4. Выбирает фотографию предмета.
5. В правой панели появляется preview референса.
6. Нажимает «Сгенерировать интерьер».
7. Клиент отправляет интерьер, референс и координаты в `/api/generate`.
8. Backend создаёт маску вокруг точки и отправляет edit-запрос в модель.
9. Результат сохраняется в R2 и добавляется в историю.

Пример тела запроса:

```json
{
  "roomImage": "data:image/jpeg;base64,...",
  "referenceImage": "data:image/png;base64,...",
  "placement": {
    "x": 0.52,
    "y": 0.67
  },
  "outputSize": "1536x1024"
}
```

### 9.2. Замена по референсу

1. Выбрать «Заменить».
2. Поставить точку в центре заменяемого предмета.
3. Загрузить фотографию нового предмета.
4. Проверить preview.
5. Запустить генерацию.

Backend получает:

```json
{
  "roomImage": "data:image/...",
  "referenceImage": "data:image/...",
  "replacement": {
    "name": "выбранный предмет",
    "mask": "data:image/png;base64,..."
  },
  "outputSize": "1536x1024"
}
```

Основное требование промпта: изменить только локально выбранный предмет, сохранить композицию, геометрию, свет и все остальные пиксели максимально близкими к исходнику.

### 9.3. Удаление

1. Выбрать «Удалить».
2. Поставить точку на предмете.
3. Операция запускается без референса.
4. Backend создаёт маску и просит восстановить фон внутри неё.

Запрос содержит `removal`, но не `referenceImage`.

### 9.4. Корректировка текстом

Для небольшой правки можно отправить instruction, например:

```text
Подними люстру выше. Больше ничего не меняй.
```

Backend получает `adjustment.instruction` и локальную маску, если она задана.

### 9.5. Требования к референсам

- JPEG, PNG или WebP.
- Предмет должен быть хорошо виден.
- Желателен нейтральный или белый фон.
- Чем меньше лишних предметов в кадре, тем выше точность.
- Для мебели желательно фото в близком к целевому ракурсе.
- Данные нельзя отправлять как ссылку `file://` — браузер должен прочитать файл в data URL.

## 10. Каталог товаров NORR

### 10.1. Источник

```text
https://norrmobler.ru/yml.php
```

Backend загружает YML/XML, разбирает категории и предложения и преобразует их в единый JSON-формат.

### 10.2. Нормализованная карточка товара

```ts
type CatalogProduct = {
  id: string;
  name: string;
  article?: string;
  image?: string;
  images: string[];
  url?: string;
  price?: number;
  oldPrice?: number;
  available: boolean;
  category?: string;
  subtype?: string;
  color?: string;
  material?: string;
  width?: number;   // мм
  depth?: number;   // мм
  height?: number;  // мм
  description?: string;
  parameters: Record<string, string>;
};
```

Главное изображение выбирается так:

1. URL с `/main/01`;
2. любое изображение с `/main/`;
3. первое доступное изображение.

### 10.3. Категории и соответствия

| Тип интерфейса | Что попадает из фида |
|---|---|
| Диван | диваны всех типов, модули диванов, кушетки |
| Кресло | кресла всех типов |
| Стул | стулья |
| Стол обеденный | обеденные столы |
| Стол журнальный | журнальные и приставные столы |
| Стол письменный / туалетный | письменные и туалетные столы |
| Кровать | кровати |
| Комод | комоды |
| TV-тумба | TV-тумбы и телевизионные тумбы |
| Ковёр | ковры |
| Светильник | вся категория света |
| Декор для дома | зеркала, аксессуары, декор, статуэтки, вазы, подушки |

### 10.4. API каталога

```http
GET /api/catalog?type=sofa&page=1&limit=12
GET /api/catalog?type=sofa&q=WAVE&page=1&limit=12
GET /api/catalog?type=sofa&subtype=Модуль&available=1&page=1&limit=12
GET /api/catalog?ids=123,456,789
```

Параметры:

- `ids` — получить конкретные товары;
- `type` — тип интерфейса;
- `q` — название или артикул;
- `subtype` — подкатегория;
- `available=1` — только товары в наличии;
- `page` — страница;
- `limit` — 6–30 товаров.

Ответ:

```json
{
  "products": [],
  "total": 1062,
  "page": 1,
  "limit": 12,
  "subtypes": ["Кушетка", "Модуль", "П-образный"]
}
```

### 10.5. Производительность каталога

- Фид кэшируется в памяти backend на 30 минут.
- UI запрашивает по 12 карточек.
- Следующая страница подгружается при приближении к низу списка.
- Кнопки «Показать ещё» нет.
- Контейнер каталога имеет собственный вертикальный scroll.
- Карточки не должны сжиматься при большом количестве товаров.
- Для изображений используется lazy loading.

## 11. Добавление товара из каталога в разделе «Мебель»

### 11.1. Одиночная операция

1. Выбрать «Добавить» или «Заменить».
2. Поставить точку.
3. Нажать «Добавить из каталога».
4. Сначала выбрать категорию, чтобы не загружать весь фид.
5. При необходимости выбрать подкатегорию.
6. Найти товар по названию или артикулу.
7. Выбрать карточку.
8. Вернуться к изображению.
9. Нажать «Сгенерировать интерьер».

В задаче сохраняются:

- действие `add` или `replace`;
- координата;
- ID товара;
- название;
- главное изображение;
- при наличии — реальные габариты.

### 11.2. Пакетная операция

Можно подготовить до пяти изменений:

1. Поставить точку на первом месте.
2. Выбрать первый товар.
3. Поставить следующую точку.
4. Выбрать следующий товар.
5. Повторить до пяти раз.
6. Запустить одну пользовательскую операцию.

Текущая реализация выполняет изменения последовательно: результат первого edit становится входом второго edit. После завершения создаётся одна запись истории с подписью «Изменено предметов: N».

> Риск: последовательные перегенерации могут накапливать отклонения. В новой ветке предпочтительно перейти к одному edit-запросу с несколькими локальными масками или к композиции по слоям, если модель/API это поддерживают надёжно.

### 11.3. Загрузка изображения товара на backend

Backend разрешает удалённую загрузку изображения только:

- по HTTPS;
- с доверенного домена `norrmobler.ru`;
- с валидным `image/*` Content-Type;
- размером не более 15 МБ.

Изображение скачивается сервером и прикладывается к OpenAI edit-запросу как файл. Нельзя просто передавать URL в модель и рассчитывать, что она его загрузит.

## 12. Генерация изображений

### 12.1. Endpoint

```http
POST /api/generate
```

Требует авторизованного пользователя и серверную переменную `OPENAI_API_KEY`.

### 12.2. Поддерживаемые операции

| Поле | Операция |
|---|---|
| `planRender` | визуализация из планограммы |
| `upscale: true` | улучшение качества |
| `replacement` | замена предмета |
| `removal` | удаление предмета |
| `adjustment` | текстовая корректировка |
| `placement` + `referenceImage` | добавление референса |
| `product` | текстовое добавление товара |
| только `prompt` | базовая генерация |

### 12.3. Модель

Модель задаётся серверной константой в `lib/image-model.ts`:

```ts
export const IMAGE_MODEL = "gpt-image-2.5-sunburst";
```

Если название модели или провайдер меняется, модифицировать нужно только серверный слой. UI-контракт должен остаться прежним.

### 12.4. Ответ

При успехе endpoint возвращает бинарный WebP. Клиент должен читать ответ как `Blob`, а не как JSON.

При ошибке backend возвращает JSON с объяснением. Перед вызовом `response.json()` нужно проверить `Content-Type`, иначе HTML-страница ошибки приведёт к `Unexpected token '<'`.

### 12.5. Сохранение и учёт

После успеха:

1. WebP записывается в R2.
2. В D1 записывается генерация.
3. Фиксируются:
   - operation;
   - prompt;
   - output key;
   - content type;
   - bytes;
   - input tokens;
   - output tokens;
   - total tokens.

## 13. Планограмма

### 13.1. Помещение

- Все размеры в миллиметрах.
- По умолчанию: 6000 × 4500 мм.
- Границы помещения можно растягивать.
- Масштаб автоматически подстраивается под рабочую область.
- Есть ручной zoom `− / +`.

### 13.2. Предметы

Доступны:

- диван;
- стол;
- кресло;
- стул;
- ковёр;
- кровать;
- шкаф;
- комод;
- TV-тумба;
- торшер / светильник;
- растение;
- декор.

Окно и дверь существуют в типах данных, но удалены из текущего списка добавления согласно последней логике интерфейса.

### 13.3. Управление предметом

- Один drag — перемещение.
- Двойной клик — режим редактирования.
- В режиме редактирования появляются 8 маркеров размера.
- В правом sidebar доступны ручные ширина и глубина.
- Поворот выполняется drag за поворотный маркер.
- Клик по свободному месту снимает выделение и скрывает маркеры.
- Правый клик открывает меню:
  - добавить/заменить референс;
  - добавить из каталога;
  - удалить предмет.
- Контекстное меню должно быть выше всех предметов по `z-index`.

Для ковра есть формы:

- прямоугольный;
- круглый, растягиваемый в овал.

Схематические формы должны показывать ориентацию мебели: у дивана, кресла и стула видны спинка и сиденье; свет обозначается кругом с крестом.

### 13.4. Каталог в планограмме

1. Правый клик по предмету.
2. «Добавить из каталога».
3. Тип каталога определяется по виду предмета.
4. Выбранный товар заменяет название и сохраняет ID.
5. Если в фиде есть размеры, плановый предмет принимает реальные width/depth.
6. В объекте планограммы сохраняются изображения, URL, артикул, цена, старая цена, параметры и описание.

Это позволяет затем:

- передать точные референсы в генерацию;
- сформировать коммерческое предложение;
- восстановить товарные данные по ID.

### 13.5. Пол и стены

Пользователь может добавить:

- референс пола;
- референс стен.

Если референс отсутствует, модель выбирает материал самостоятельно. Если он указан, prompt требует использовать именно его.

### 13.6. Камера

1. Двойной клик по свободной области устанавливает камеру.
2. Камеру можно перетащить.
3. В правом sidebar задаётся высота от пола:
   - минимум 300 мм;
   - максимум 3000 мм;
   - шаг 50 мм;
   - значение по умолчанию 1500 мм.
4. Направление камеры автоматически ориентируется в центр комнаты.
5. Позиция, высота и rotation добавляются в prompt.
6. Маркер камеры входит в plan image.

Текущее состояние камеры хранится в `sessionStorage` по ключу:

```text
room-plan-camera
```

Это временное хранение. Для полноценного продолжения проекта камеру нужно перенести в `projects.state_json`.

### 13.7. Создание визуализации

Кнопка «Создать визуализацию» активна, если на плане есть хотя бы один предмет.

Клиент отправляет:

```json
{
  "planRender": {
    "planImage": "data:image/png;base64,...",
    "room": {
      "width": 6000,
      "length": 4500
    },
    "items": [
      {
        "name": "Диван WAVE",
        "width": 2600,
        "depth": 1050,
        "x": 0.25,
        "y": 0.35,
        "rotation": 90,
        "referenceName": "WAVE"
      }
    ],
    "referenceImages": ["data:image/jpeg;base64,..."]
  }
}
```

В один запрос передаётся до 8 reference images. После генерации пользователь переводится в раздел «Мебель», а результат добавляется в историю как «Интерьер по планограмме».

## 14. Апскейл

Апскейл применяется к активной версии:

```json
{
  "roomImage": "data:image/webp;base64,...",
  "upscale": true,
  "outputSize": "1536x1024"
}
```

Требование к модели: улучшить детализацию и резкость, не менять композицию, предметы, цвета и кадр.

Результат:

- добавляется в историю;
- становится активным;
- сохраняется в R2;
- учитывается как отдельная генерация.

## 15. Коммерческое предложение PDF

### 15.1. Запуск

Рядом с «Сохранить» и сердцем есть кнопка печати. Она открывает меню:

- «С ценами»;
- «Без цен».

### 15.2. Состав PDF

1. Первая страница — постоянная обложка из `public/proposal-cover.png`.
2. Вторая страница — активная визуализация проекта.
3. Третья и следующие — по одной карточке на каждый уникальный каталоговый товар из планограммы.

Товарные данные перед созданием PDF повторно запрашиваются по ID из каталога, чтобы получить актуальные характеристики и цены.

### 15.3. Карточка товара

Содержит:

- название;
- артикул;
- категорию и подтип;
- ширину, высоту, глубину;
- материал, цвет и дополнительные параметры;
- описание;
- главное изображение;
- второе интерьерное изображение, если оно есть;
- цену и старую цену в версии «С ценами»;
- обозначение валюты `руб.`.

### 15.4. API

```http
POST /api/proposal
Content-Type: application/json
```

Основные поля:

```json
{
  "projectName": "102",
  "proposalCoverImage": "data:image/png;base64,...",
  "coverImage": "data:image/webp;base64,...",
  "fontData": "data:font/ttf;base64,...",
  "withPrices": true,
  "products": []
}
```

Endpoint отвечает:

```http
Content-Type: application/pdf
Content-Disposition: inline; filename="commercial-proposal-102.pdf"
Cache-Control: no-store
```

Клиент создаёт Blob URL и открывает его в новой вкладке. Вкладка должна открываться синхронно с пользовательским кликом, а URL присваивается после готовности Blob — это предотвращает блокировку popup. При ошибке пустая вкладка должна закрываться, а ошибка показываться в текущем интерфейсе.

## 21. Как добавить новый API или провайдера

### 21.1. Не менять UI-контракт без необходимости

Лучший способ замены OpenAI на другой image provider:

1. Оставить `/api/generate` публичным контрактом приложения.
2. Создать серверный adapter, например:

```ts
interface ImageProvider {
  generate(input: GenerateInput): Promise<GenerateResult>;
  edit(input: EditInput): Promise<GenerateResult>;
  upscale(input: UpscaleInput): Promise<GenerateResult>;
}
```

3. Преобразовать текущий request в provider-specific payload.
4. Нормализовать ответ обратно в WebP + usage.
5. Сохранить прежний R2/D1 pipeline.

Так можно тестировать Gemini или другую модель без переписывания интерфейса, проектов, истории и кабинета.

### 21.2. Новый внешний каталог

Для подключения нового фида:

1. Создать серверный parser.
2. Привести данные к `CatalogProduct`.
3. Реализовать типовые mappings.
4. Настроить whitelist доменов картинок.
5. Добавить tenant catalog configuration.
6. Не менять UI `/api/catalog`, если можно сохранить контракт.

### 21.3. Обязательные проверки нового API

- timeout;
- повтор запроса только для безопасных ошибок;
- лимит размера файла;
- проверка MIME;
- защита от SSRF;
- обработка HTML вместо JSON;
- учёт стоимости;
- сохранение provider request ID;
- tenant/user isolation;
- понятная ошибка в UI.

## 23. Инварианты — что нельзя ломать дополнением

1. Все API-ключи остаются на backend.
2. Все проектные запросы изолированы по user + tenant.
3. История не очищается при загрузке нового интерьера.
4. Новая генерация всегда добавляет версию, а не перезаписывает исходник.
5. Активная история определяет вход следующей операции.
6. Соотношение сторон изображения сохраняется.
7. Каталог загружается постранично и не блокирует UI тысячей карточек.
8. Товар из каталога передаётся в модель реальным image file, не только URL.
9. PDF открывается как `application/pdf` inline.
10. Ошибки API не интерпретируются вслепую как JSON.
11. Плановые размеры всегда в миллиметрах.
12. Отсутствующие стены/пол/камера дают модели свободу; указанные параметры обязательны.
13. Сохранённый проект должен открываться в том же состоянии, в котором был сохранён.

## 24. Известные технические долги

1. Полное состояние планограммы ещё не сохраняется backend-контрактом проекта.
2. Камера хранится только в `sessionStorage`.
3. Пакет из пяти мебельных правок выполняется последовательными edit-запросами и может накапливать галлюцинации.
4. Кэш каталога находится в памяти instance; для нескольких edge instances лучше использовать KV/R2/D1 cache с ETag.
5. Распознавание/сегментация/слои остаются экспериментальными.
6. Billing rates зашиты как внутренние константы.
7. Нужна очередь/асинхронный job status для долгих image operations вместо одного долгого HTTP-запроса.
8. Следует хранить provider/model/version для каждой генерации.
9. Нужны автоматические e2e-тесты критических сценариев.
